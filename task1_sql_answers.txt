QUESTION 1 – HOW MUCH IS EACH MEMBER BORROWING?
------------------------------------------------
Business question:
How many checkouts has each library member made, including members who have
not borrowed anything?

Reasoning:
A LEFT JOIN is used from members to checkouts so that every member appears in
the result, including members with zero checkouts. COUNT(c.checkout_id) counts
only actual checkout records, so members with no matching checkout receive 0.

SQL:
SELECT m.member_id, m.first_name, COUNT(c.checkout_id) AS total_checkouts
FROM members m
LEFT JOIN checkouts c ON m.member_id = c.member_id
GROUP BY m.member_id, m.first_name
ORDER BY m.member_id;

Reasoning:
The books table is searched using LIKE with the pattern '%Samir%'. This finds

QUESTION 3 – WHAT ARE THE FIVE MOST POPULAR BOOKS?
---------------------------------------------------
Business question:
Which five books have been checked out the most?

Reasoning:
The checkouts table is joined to books so the book titles and authors can be
shown. The checkout records are grouped by book, counted, sorted from highest
to lowest, and limited to the top five.

SQL:
SELECT b.title, b.author, COUNT(c.checkout_id) AS checkout_count
FROM checkouts c
JOIN books b ON c.book_id = b.book_id
GROUP BY c.book_id
ORDER BY checkout_count DESC
LIMIT 5;

QUESTION 4 – WHO ARE THE TEN MOST ACTIVE READERS?
--------------------------------------------------
Business question:
Which ten members have borrowed the most books?

Reasoning:
The checkouts table is joined to members so the result can identify each
reader. The checkout records are grouped by member, counted, ordered from the
largest count to the smallest, and limited to ten members.

SQL:
SELECT m.member_id, m.first_name, m.last_name,
       COUNT(c.checkout_id) AS checkout_count
FROM checkouts c
JOIN members m ON c.member_id = m.member_id
GROUP BY c.member_id
ORDER BY checkout_count DESC
LIMIT 10;

Chosen neighborhood:

Reasoning:
The members table is joined to checkouts so that only checkouts belonging to
Maadi members are included. The results are ordered from newest to oldest.

SELECT c.member_id, c.checkout_date, m.neighborhood

DATA COMBINATION
----------------
Stage 1 – Members and Checkouts
The database checkouts were combined with member information using Python
pandas. The merge used member_id as the matching key. A separate groupby count
was created to calculate total_checkouts for every member. The member
information was merged with this count using a left merge so that members with
zero database checkouts were still represented.

Stage 1 result:
391 rows and 12 columns.

Stage 2 – Book Details
The database books were merged with the JSON book catalog using book_id.
This adds additional book information such as genre, pages, publication year,
and publisher. The result was then merged into the Stage 1 checkout data.

Stage 2 result:
391 rows and 19 columns.

The number of database checkouts remained 391, which confirms
that adding book information did not add or remove checkout records.

Stage 3 – Reading Kickoff Checkouts
The Reading Kickoff HTML table was read with pandas.read_html(). Its columns
were renamed to match the database structure: member_id, book_id, and
checkout_date. A return_date column was added as a missing value because the
web page does not provide return dates. A source column was also added to
identify these records as Reading Kickoff records.

The Reading Kickoff data contains 26 checkout records.

Final combined dataset:
- Total rows: 417
- Total columns: 19
- Database records: 391
- Reading Kickoff records: 26
- Output file: task1_combined_data.csv

Final columns:
checkout_id, member_id, book_id, checkout_date, return_date, first_name, last_name, grade, neighborhood, membership_status, join_date, total_checkouts, title, author, genre, pages, publication_year, publisher, source

REFLECTION – WEB PAGE VS DATABASE
---------------------------------
The library database and the Reading Kickoff web page are different types of
data sources. A database is designed to store structured records and allows
SQL queries to retrieve specific information accurately and efficiently. In
this task, the database provided separate tables for members, books, and
checkouts, with keys such as member_id and book_id that made the relationships
between the tables clear.

The Reading Kickoff source was an HTML web page designed primarily for people
to read in a browser. Before the data could be combined with the database
records, the table had to be extracted from the HTML page and its column names
and data types had to be standardized. This was different from querying the
database because the web page did not provide the same structured database
tables or relationships.

An API would normally be more convenient for a program because it is designed
to return structured data in a predictable format. A web page, on the other
hand, may require HTML parsing and additional cleaning before the data can be
used. This distinction mattered in this project because the Reading Kickoff
records came from a web page, so pandas.read_html() was needed to turn the
human-readable table into a DataFrame that could be combined with the database
and catalog data.

Overall, the project demonstrated why understanding the source of data is
important. The database was queried directly for the five business questions,
while Python was used to combine the different sources and standardize their
structure. Keeping the source information in the final dataset also makes it
easier to understand where each checkout record came from.
